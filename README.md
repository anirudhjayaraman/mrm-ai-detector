# mrm-ai-detector

[![PyPI](https://img.shields.io/pypi/v/mrm-ai-detector.svg)](https://pypi.org/project/mrm-ai-detector/)
[![Python](https://img.shields.io/pypi/pyversions/mrm-ai-detector.svg)](https://pypi.org/project/mrm-ai-detector/)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](https://github.com/anirudhjayaraman/mrm-ai-detector/blob/main/LICENSE)

**Screen model documentation for heavy AI reliance**: model development and
methodology documents, validation reports, audit issues, MRM policies,
monitoring packs and review e-mails.

AI use in model development and validation is often encouraged. The point of
this tool is narrower: to show *where* a document leans on generated text, so a
reviewer can check that those sections rest on real analysis. A high score is a
prompt for a manual check, not a finding.

**What it catches, and what it doesn't** (details in [Benchmark summary](#benchmark-summary)):
generic or template-filling AI text, text from open models, ChatGPT-3.5-era
text and heavy AI rewrites are detected reliably, at a low false-positive rate
on genuine MRM documents. **Current frontier models (GPT-4o/5, Claude) writing
from the author's own results are not**: neither this tool nor any other
detector we tested, including a full-size Binoculars and a commercial web
detector, could separate that text from human writing. For those files the
[provenance hints](#provenance-hints) are often more informative than the
style score.

* **Zero-dependency core.** Pure Python standard library, 3.9+. `pip install mrm-ai-detector` pulls in nothing else.
* **Built for MRM text.** Features include evidence density (test statistics,
  data windows, model IDs, regulatory cross-references) and *unsupported
  evaluative claims* ("the model is robust and well-calibrated" with nothing
  behind it), alongside LLM-style markers and stylometry.
* **Calibrated and benchmarked on real MRM literature.** Human-written
  documents (Fed SR 11-7, PRA SS3/18 and CP6/22, ECB TRIM, Fed and FHFA OIG
  model-validation reviews, GAO model reviews, Fed DFAST model documentation,
  q-fin papers) against AI-written MRM text from several model families. See
  [benchmarks/](https://github.com/anirudhjayaraman/mrm-ai-detector/tree/main/benchmarks).
* **Optional ensemble with open-source detectors** (`--lm`). Binoculars and
  Fast-DetectGPT (zero-shot), plus the HC3, Fakespot (2025) and Desklib (2025)
  classifiers. On their own, the 2025 classifiers flag a third or more of human
  regulatory text in our benchmark. Inside the calibrated ensemble their
  false positives are kept in check.
* **Explainable output.** Per-segment scores, the top contributing signals, a
  bootstrap confidence interval, and *mixed-authorship* detection that flags
  which sections look AI-written. Tables, caption lists and code listings are
  reported but not scored.
* **Provenance hints.** Traces that AI tools leave in files, independent of
  style: Word files generated by `python-docx` (how ChatGPT's file tool makes
  them), non-breaking hyphens and narrow spaces that assistants emit,
  `utm_source=chatgpt.com` links, `oaicite` citation markers, chat-style
  openers. Reported separately; they never change the probability.
* **Tested on partially AI-written documents.** 106 documents mixing real
  pre-2022 MRM text with AI-polished, rewritten, notes-to-prose, continued and
  summary sections, plus the public APT-Eval and MixSet benchmarks.
* **Reads what colleagues actually send.** `.docx`, `.pdf`, `.md`, `.txt`,
  `.html`, e-mails (`.eml`, Outlook `.msg`; quoted thread history is stripped),
  and photos or screenshots via OCR (built in on macOS).

> **Read [Responsible use](#responsible-use) before applying this to anyone's work.**
> Every AI-text detector, this one included, produces false positives. A score
> is a reason to look more closely, never evidence on its own.

## Install

```bash
pip install mrm-ai-detector
```

That's the whole core: no dependencies. It reads `.txt`, `.md`, `.docx`,
`.html` and `.eml` files and, on a Mac, photos and screenshots (`.heic`,
`.jpg`, `.png` …) through Apple's built-in Live Text OCR engine. Optional
extras:

```bash
pip install "mrm-ai-detector[pdf]"     # PDF support (pypdf)
pip install "mrm-ai-detector[email]"   # Outlook .msg support (olefile)
pip install "mrm-ai-detector[ocr]"     # photos/screenshots on Windows/Linux (RapidOCR); macOS needs nothing
pip install "mrm-ai-detector[lm]"      # language-model ensemble (torch + transformers; ~3.5 GB of models downloaded on first use)
pip install "mrm-ai-detector[all]"     # everything
```

To try it without installing anything permanently, use
[`uv`](https://docs.astral.sh/uv/) or [`pipx`](https://pipx.pypa.io/):

```bash
uvx --from mrm-ai-detector mrm-detect scan report.docx
```

To install the latest development version straight from GitHub:

```bash
pip install "git+https://github.com/anirudhjayaraman/mrm-ai-detector"
```

## Quick start

```bash
mrm-detect scan report.docx                 # one document
mrm-detect scan ~/Downloads/IMG_1234.HEIC   # a photo or screenshot (macOS: built-in OCR)
mrm-detect scan reports/ --summary          # a whole folder
```

The repository's `examples/` folder shows what to expect. After cloning, it
also runs without installing: `python -m mrm_ai_detector scan examples/`.

```
Document                                              Words  AI prob  AI share  Verdict
----------------------------------------------------------------------------------------------------
examples/ai_generated_methodology_qwen.md               561      90%       65%  Likely AI-generated
examples/ai_generated_validation_summary_claude.md      364      11%        0%  Likely human-written
examples/human_sr11-7_validation_excerpt.txt            723      52%        0%  Inconclusive
examples/mixed_validation_report.md                    1284      26%        0%  Likely human-written
```

The examples were chosen to show the limits honestly. Text from a small open
model is caught, but the Claude-written summary passes as human, and so does
the report with an inserted Claude-written section. SR 11-7, a human text,
sits in the inconclusive band. See [Benchmark summary](#benchmark-summary).

## Usage

```bash
mrm-detect scan report.docx                       # detailed text report
mrm-detect scan reports/ --summary                # one line per document
mrm-detect scan reports/ -f html -o report.html   # self-contained HTML report with highlighted segments
mrm-detect scan issue.msg -f json                 # machine-readable
mrm-detect scan report.pdf --lm                   # add Binoculars / Fast-DetectGPT / HC3 / Fakespot / Desklib features
cat draft.txt | mrm-detect scan -                 # stdin
mrm-detect scan submissions/ --fail-on-ai         # exit code 3 if anything is flagged (CI / workflow gate)
mrm-detect features report.docx                   # raw feature values, for analysts
```

Python API:

```python
from mrm_ai_detector import Detector

result = Detector().analyze_file("validation_report.docx")
print(result.verdict, f"{result.probability:.0%}", f"(90% CI {result.ci_low:.0%}–{result.ci_high:.0%})")
for seg in result.segments:
    if seg.flagged:
        print(seg.section, f"{seg.probability:.0%}", [s.feature for s in seg.signals])
```

### Verdicts

| Verdict | Meaning |
|---|---|
| Likely AI-generated | Document probability ≥ the model's AI threshold (calibrated for ≤ 2% false positives on human MRM documents) |
| Mixed: partially AI-generated | Not flagged overall, but ≥ 15% of the text sits in segments that individually exceed the threshold |
| Likely human-written | Probability ≤ 30% and no material flagged sections |
| Inconclusive | Anything in between |
| Insufficient text | Fewer than 150 words of prose. Detection is unreliable on short text |

A "Likely human-written" verdict means the text didn't trip the detector. It is
**not** evidence of human authorship: see the frontier-model results below.

## How it works

1. **Ingest and normalise.** Text is extracted, PDF line breaks reflowed,
   running headers and footers removed, and e-mail threads cut to the newest
   message. Prose inside table cells is kept, since audit issues are often
   written in tables.
2. **Segment.** The text is split into roughly 180-word chunks. Headings are
   treated as soft boundaries, so heading-dense validation reports still give
   scorable chunks.
3. **Features** (`mrm-detect features` lists them all):
   * *Domain evidence.* Numeric density, metric statements with values (Gini
     0.61, PSI = 0.08), specific references (model IDs, dates, SR 11-7,
     "Section 4.2"), the ratio of unsupported evaluative claims, governance
     boilerplate, hedging.
   * *LLM markers.* Weighted lexicon ("delve", "it is important to note",
     "plays a pivotal role" …) with MRM vocabulary such as "robust" and
     "comprehensive" down-weighted. Also stock sentence openers, ", ensuring
     …" participle tails, "not only … but", and triplets.
   * *Stylometry.* Sentence-length burstiness, lexical diversity, word length,
     function words, punctuation habits.
   * *Information theory.* Windowed compression ratio, character-trigram
     entropy, phrase repetition.
   * *Optional language-model features* (`--lm`). Binoculars (Hans et al.,
     ICML 2024) and Fast-DetectGPT (Bao et al., ICLR 2024) with a
     Qwen2.5-0.5B observer/performer pair, plus the logits of three
     open-source classifiers: HC3 RoBERTa (Guo et al., 2023), Fakespot RoBERTa
     (2025) and Desklib DeBERTa-v3 (2025).
4. **Score.** Features are standardised against the calibration corpus and
   combined by an L2-regularised logistic model. Logits on short texts are
   shrunk towards 50% ("no evidence"). A sentence bootstrap gives a 90%
   confidence interval.
5. **Explain.** Every score comes with the features that pushed it up or down.
   Chunks that aren't running prose (tables, figure-caption lists, code or
   package listings) are shown but not scored.
6. **Provenance.** Independently of the score, the file is checked for traces
   of AI tools (see [Provenance hints](#provenance-hints)).

## Benchmark summary

Held-out documents never used in training are split by document, and every
human document predates ChatGPT. Full tables are in
[`benchmarks/results/`](https://github.com/anirudhjayaraman/mrm-ai-detector/tree/main/benchmarks/results). Reproduce them with the
commands in [benchmarks/README.md](https://github.com/anirudhjayaraman/mrm-ai-detector/blob/main/benchmarks/README.md).

### Head-to-head on 331 held-out documents (102 in-domain MRM documents)

| Detector | In-domain doc AUC | In-domain TPR @ 5% FPR | All-doc AUC | Doc TPR / FPR at its own threshold |
|---|---:|---:|---:|---|
| **mrm-detector `--lm`** (this package, ensemble) | **0.965** | **0.891** | **0.986** | 0.895 / **0.006** |
| Fakespot RoBERTa (2025) | 0.931 | 0.848 | 0.965 | 0.947 / 0.163 |
| Desklib DeBERTa-v3 (2025) | 0.924 | 0.870 | 0.962 | 0.930 / 0.138 |
| **mrm-detector** (stdlib only, zero install) | 0.920 | 0.739 | 0.929 | 0.515 / **0.000** |
| HC3 ChatGPT RoBERTa (2023) | 0.758 | 0.326 | 0.923 | 0.620 / 0.013 |
| RADAR (2023) | 0.636 | 0.130 | 0.823 | 0.655 / 0.175 |
| Binoculars (Qwen2.5-0.5B pair) | 0.502 | 0.109 | 0.787 | n/a |
| Fast-DetectGPT (Qwen2.5-0.5B) | 0.406 | 0.087 | 0.741 | n/a |
| OpenAI GPT-2 output detector (2019) | 0.398 | 0.043 | 0.798 | 0.550 / 0.037 |

Fakespot and Desklib, used on their own, flag a third or more of human
regulatory and supervisory documents. Inside the ensemble one of 160 held-out
human documents is flagged: SR 11-7 itself, at 52% against a 50% threshold (it
scored 49% before the v1.1 retraining; free web detectors rate it up to 95.5% AI).

**Detection rate by generator (ensemble, held-out documents):** Qwen2.5 100%,
SmolLM2 100%, Phi-3.5 100%, gpt-3.5-turbo / ChatGPT 100%, Cohere 100%,
Flan-T5 73%, **text-davinci-003 20%, Claude 33%**.

### Partially AI-written documents

[`build_mixed.py`](https://github.com/anirudhjayaraman/mrm-ai-detector/blob/main/benchmarks/build_mixed.py) takes ~1,500-word windows of
pre-2022 MRM documents and has an assistant do what authors actually ask for:
lightly polish a paragraph, rewrite it, turn notes into prose, continue the
text, or write a "key findings" section from it. Every word keeps its label.
106 documents (Qwen2.5-7B, Llama-3.1-8B, Gemma-2-9B and Claude); results on the
51 built from held-out source documents, `--lm` model:

| True AI share of the document | Docs | Predicted AI share | Document flagged |
|---|---:|---:|---:|
| 0% | 7 | 3% | 0% |
| 1–35% | 13 | 25% | 23% |
| 35–70% | 16 | 41% | 69% |
| 70–100% | 15 | 85% | 93% |

* AI-written sections vs untouched human sections: segment AUC 0.95, 82% of
  AI sections flagged at a 4.7% false-flag rate. Notes-to-prose, continuation
  and summaries are caught most often (84–93%); faithful rewrites less so (60%).
* Lightly polished human paragraphs are mostly left alone, which is the
  intended behaviour: on APT-Eval (human text polished by GPT-4o, DeepSeek-V3
  and Llama-3.1-70B), 11–17% of "minor" polishes are flagged against 83% of
  "major" rewrites. On MixSet, GPT-4 completions are flagged 100% of the time.
* **By generator:** Gemma 95%, Qwen 88% and Llama 76% of AI sections flagged;
  **Claude 0 of 8.**

### The limit: frontier models writing from the author's own material

The hardest case is also the most realistic one: a current model (GPT-4o/5,
Claude) drafting technical prose from the author's own results, code and notes.
We tested it on a real 16,000-word quantitative-finance report (the package
author's own CQF final project, written with heavy ChatGPT assistance and
then redrafted), including the unedited ChatGPT-generated Word drafts of its
conclusions chapter:

| Detector | ChatGPT drafts, unedited | Final report |
|---|---|---|
| mrm-detector `--lm` | 0.3% ("Likely human") | ~3% |
| Binoculars with a 7B observer/performer pair (Qwen2.5-7B, MLX 4-bit) | 0 of 14 segments flagged; scored *more* human than pre-2022 papers | 1 of 64 segments flagged |
| HC3, Fakespot, Desklib classifiers | strongly "human" | strongly "human" |
| A commercial web detector (JustDone) | – | 0% AI |

Grounded frontier-model text in a formal technical register looked like human
writing to every method we had (the lightweight model flagged 17% of the
drafts' text, far short of the truth). What *did* identify the drafts were file
traces: all five were flagged by the [provenance hints](#provenance-hints)
(`python-docx` metadata; three of them also carried 37–67 non-breaking hyphens),
and every one of the 99 non-breaking hyphens in the final Word file sits in the
chapter that came from those drafts.

### Free web detectors on 8 short samples (held out for this package too)

Four human samples are pre-2023 US federal texts (SR 11-7, Fed OIG, GAO, FHFA
OIG). Three AI samples are Claude-written MRM text and one is Qwen2.5-written.

| Detector | AI samples caught | Human samples falsely flagged |
|---|---|---|
| GPTZero (free tier) | 4 / 4 | 1 / 4 (FHFA OIG 2020 report: 100% AI) |
| mrm-detector `--lm` | 2 / 4 | 1 / 4 (SR 11-7 excerpt: 66%) |
| ZeroGPT | 1 / 4 | 0 / 4 |
| mrm-detector (stdlib) | 1 / 4 | 0 / 4 |
| Sapling | 1 / 4 | 2 / 4 (SR 11-7: 95.5%, FHFA OIG: 71.9%) |

Per-sample numbers are in [`benchmarks/results/web_comparison.md`](https://github.com/anirudhjayaraman/mrm-ai-detector/blob/main/benchmarks/results/web_comparison.md).

### What this means in practice

* Generic, template-filling AI text and text from open models are detected
  reliably, including when they are mixed into human documents, with a low
  false-positive rate on genuine MRM documents.
* Light AI polishing is mostly not flagged, by design.
* **Frontier-model text grounded in the author's own work is not detected**, by
  this tool or by the others we tested. "Likely human-written" is therefore not
  evidence of human authorship. Read the [provenance hints](#provenance-hints),
  compare against the [author's own earlier work](#comparing-against-an-authors-own-earlier-work),
  and review the substance: do the numbers tie back to the outputs, and do the
  claims match the code and data?

## Provenance hints

Every `scan` also inspects the file itself for traces that AI tools leave,
independent of writing style. They are listed under *Provenance hints* in each
report (and in JSON as `provenance`) and never change the probability.

| Hint | Strength | Why |
|---|---|---|
| Word file created by `python-docx` (creator/description metadata) | strong | how ChatGPT's file tool builds `.docx` files |
| Creation date 2013-12-23 23:15 | moderate | the python-docx default template date |
| `utm_source=chatgpt.com` in links; `:contentReference[oaicite:N]`, `turnNsearchN`, `【4†source】` | strong | left behind when copying from ChatGPT or other assistants |
| Non-breaking hyphens (U+2011) / narrow no-break spaces (U+202F) in volume | moderate–weak | assistants emit them; keyboards rarely do |
| "Certainly! Here's …", "Would you like me to draft …", `[Insert …]` | moderate | chat or template leftovers |
| "Generated on <timestamp>" lines; PDFs produced by ReportLab and similar | weak | common in generated files, but also in reporting systems |

On the 624 human benchmark documents (42 PDFs and 582 text files) no hint fired.
A hint is a reason to ask how a document was produced, not proof: anyone can
type a non-breaking hyphen, and a person may have used ChatGPT only to format
their own text into Word.

## Comparing against an author's own earlier work

Generic detectors judge everyone against one population, so writers whose
natural style is formal, template-driven or non-native get flagged more often.
The **baseline** mode asks a fairer question: *is this document unusual for
this person?*

```bash
mrm-detect baseline new_issue_writeup.docx --reference colleague_2019_2022_docs/
```

```text
# illustrative output
Style distance: 1.84  (author's own documents: median 0.71, 90th pct 1.02)
Empirical p-value: 0.08   Shift towards AI-typical features: +0.62
Unusual for this author, and the shift is towards LLM-typical writing. Worth a closer look.
Largest shifts (z vs author's own writing):
  +2.91 AI-ward  ai_marker_rate ...
```

Use at least 5 reference documents, ideally 10 or more, of the same genre
(issue write-ups against issue write-ups) from before 2023. A low p-value with
an AI-ward shift is a reason to talk to the author, not a conclusion.

## Calibrating on your organisation's documents

The shipped calibration uses public documents. Your organisation's house style
will differ, so **calibrate locally before relying on scores**:

1. **Human set.** Collect documents written before December 2022: validation
   reports, audit issues, e-mails. Their authorship isn't in doubt.
2. **AI set.** Ask your approved LLM(s) to write comparable documents (same
   templates, same models), including prompts like "make it sound like a
   human validator wrote it".
3. Train and evaluate. Everything stays on your machine:

```bash
mrm-detect train --human corpus/human --ai corpus/ai -o our_model.json --save-dataset features.jsonl
mrm-detect evaluate --human holdout/human --ai holdout/ai --model our_model.json
mrm-detect scan new_reports/ --model our_model.json
```

`train` reports document-grouped cross-validated AUC and TPR at 1% and 5%
FPR. Choose `--threshold` from your own false-positive tolerance.

## Responsible use

* **False positives are unavoidable.** In our tests the free web detectors
  rated a 2011 Federal Reserve guidance text 95.5% AI (Sapling) and a 2020
  FHFA OIG report 100% AI (GPTZero). This tool is calibrated to keep human
  MRM documents below a 2% false-positive rate on the benchmark, but your
  documents aren't the benchmark.
* **Non-native English writers are flagged more often** by perplexity- and
  style-based detectors (Liang et al., 2023, *GPT detectors are biased against
  non-native English writers*). Formulaic, template-driven writing such as
  audit-issue templates also looks "low-perplexity". Weigh scores
  accordingly.
* **AI assistance isn't misconduct.** Translation, grammar fixes and
  structured drafting may be permitted under your firm's AI policy. Ask what
  your policy actually prohibits, and whether the *content* (evidence, numbers,
  conclusions) is sound. The domain-evidence signals in the report help with
  that question whoever wrote the text.
* **Use scores for triage, never as the sole basis** for any decision about a
  person. Keep a human in the loop, and give authors the opportunity to
  explain.
* **Confidentiality.** Everything runs locally. Nothing is sent anywhere,
  including with `--lm`, whose models are downloaded once from Hugging Face
  and run on your machine. Don't paste internal documents into web detectors.
* **OCR input is noisy.** Scan the original document rather than a photo when
  you can. Reports from OCR'd input carry a warning.

## Troubleshooting

* **`--lm` is slow the first time.** About 3.5 GB of models are downloaded
  once, then cached. Scoring runs at about 1–2 s per 180-word segment on a
  laptop.
* **Model download hangs.** Set `HF_HUB_DISABLE_XET=1`. Behind a corporate
  proxy, pre-download the models listed in
  `mrm_ai_detector/features/neural.py` and set `HF_HUB_OFFLINE=1`.
* **Memory.** `--lm` needs about 4 GB of RAM. Use
  `MRM_DETECTOR_CLASSIFIERS=hc3,fakespot` to drop the large Desklib model,
  then recalibrate.
* **Scanned PDFs.** Text-less PDFs raise an error; convert pages to images
  and scan those (OCR), or run OCR first.

## Project layout

```
mrm_ai_detector/      the package (stdlib core; neural/OCR/PDF features optional)
  text.py             normalisation, sentence splitting, segmentation
  ingest.py           .txt .md .docx .pdf .html .eml .msg, images (OCR)
  features/           domain, markers, stylometry, entropy, neural (optional)
  scoring.py          standardised logistic scoring model (JSON)
  detector.py         orchestration, bootstrap CI, verdicts
  provenance.py       file and typography traces of AI tools (reported, never scored)
  train.py            calibration: IRLS ridge logistic, grouped CV, metrics
  report.py           text / JSON / Markdown / HTML reports
  models/             shipped calibrated models
benchmarks/           corpus manifest, fetch/generate/calibrate/compare scripts, results
  build_mixed.py      partially AI-written documents (local models or openai:<model>)
  eval_mixed.py       AI-share accuracy on mixed documents, APT-Eval, MixSet
  mixed_claude/       Claude-written mixed documents (US federal public-domain sources)
tests/                pytest suite
examples/             public-domain human text, AI-written and mixed examples
```
